# 技术侧对接清单（C → A / B）

> 维护：文本侧（C）｜更新：2026-10-20
> 依据：官方题面 WJ-OW-001、智能体测评计分规则、技术报告模板
> 目的：把技术报告与答辩需要的素材，提前约定成可交付、可核查的格式

## 0. 结论先行

技术报告 10 分 + 现场答辩 40 分，合计占总分 50%。报告正文只有 3000–5000 字，评审看四件事：方案设计、工程实现、实验分析、技术表达。这四件事都必须由真实运行数据支撑，不能事后补写。

本周技术侧只需要先给三样东西：

1. 一句话技术路线：纯规则 / 规则 + LLM / 纯 LLM；若用 LLM，说明它负责哪一层（视觉判别、规划、代码生成）。
2. 代码仓库地址与运行入口：从零到能跑出一次结果的完整命令。
3. 一次完整跑通的运行目录：至少包含 `outcome.json`、`budget.json`、`review.html`，有录屏更好。

## 1. 角色与边界

| 角色 | 负责 | 不负责 |
|---|---|---|
| A（主程） | 环境动作、智能体主逻辑、状态机、动作校验与容错 | 报告文字、答辩讲稿 |
| B（LLM 层） | 模型 API、提示词、调用节奏、失败重试与降级 | 报告排版、引用整理 |
| C（文本） | 实验日志、技术报告、答辩材料、提交清单 | 代写核心代码、替技术侧做技术判断 |

C 的写作依赖 A / B 的数据；A / B 的进度也需要 C 及时记录，双方按本清单交接。

## 2. 每次实验必须登记

统一记录在 `report/实验日志.md`，一行一次实验。字段如下：

| 字段 | 说明 |
|---|---|
| 日期 / 执行人 | 例：`<日期> / <角色>`，角色用 A / B / C，不写姓名 |
| 代码版本 | git commit 短哈希；未提交则写“本地未提交”。基线对应 `f37461c` |
| 开发包版本 | 写 `code-manifest.json` 的 SHA-256 前 8 位（官网版 `5510f101`），不用“27 文件 / 24 文件”这类易失效的描述 |
| 场景 | woodcraft / stone-tools / iron-age / full-seed-N |
| 种子 | 场景里的 `world_seed` |
| 结果 | completed / error + 终止原因（iron_pickaxe、wall_time、token_limit 等） |
| 步数 | `outcome.json` 的 `metrics.action_count` |
| tokens | `budget.json` 的 `tokens` 与 `calls` |
| 分数 | tech / side / efficiency / death_penalty / 总分 |
| 失败现象 | 一句话，写“看到什么”，不写猜测 |
| 证据路径 | 小文件放 `report/evidence/E00x/`（`outcome.json` / `budget.json` / `checkpoint.json` / `review.html`）；`replay.mp4` 与 `steps.jsonl` 体积大，只记本地路径 |
| 相对上一版 | 改了什么（一句话） |

只要给出运行目录路径，C 可以自己从 `outcome.json` 和 `budget.json` 里取数；不要只回“跑通了”。

示例：

| 日期 | 版本 | 场景 / 种子 | 结果 | 步数 | tokens | 总分 | 现象 | 证据 |
|---|---|---|---|---|---|---|---|---|
| 2026-10-25 | a1b2c3d | iron-age / 44 | error / wall_time | 2310 | 4.1M | 37 | 找到铁矿但未冶炼，卡在熔炉放置 | `runs/world-xxxx/evidence/1/review.html` |

## 3. 报告五部分分别需要什么

官方模板只有五块，按它写，不另起结构。

| 报告部分 | 需要技术侧提供 | 形式 |
|---|---|---|
| 我做了什么 | 问题定义、总体路线、与官方基线的差异 | 一段话 + 一张架构图 |
| 我怎么实现 | 模块划分、状态机状态列表、LLM 调用点与间隔、8 维动作封装、失败恢复、依赖与运行命令 | 模块图 + 伪代码或流程说明 |
| 现在效果怎样 | 至少 3 组对照：规则 baseline / 加 LLM / 调参后；每组给种子、步数、分数、tokens | 表格 + 分数-步数曲线 |
| 可选研究亮点 | 一个具体发现，例：LLM 调用间隔 20 步 vs 50 步对分数与 token 的影响 | 对照数据 + 解释 |
| 引用与分工 | 论文、开源代码、模型名称与版本的来源；自己的改动；成员贡献 | 列表 |

补充要求：

- 至少 2 个成功案例、2 个失败案例；失败案例要写清“现象—原因—改法—结果”。
- 所有数字必须能追溯到某次运行目录；报告中不出现“大约”“估计”。
- 架构图、流程图、环境截图至少各一张，原图交给 C，不要截图再压缩。

## 4. 答辩素材

答辩 40 分，按以下清单准备：

- 5 分钟版与 10 分钟版讲稿各一份，结构：问题 → 方案 → 实现 → 结果 → 失败与改进。
- 架构图 1 张（答辩用大图，不是报告里的小图）。
- 分数-步数曲线 1 张，标出木 / 石 / 铁三个检查点。
- 失败案例 3 个，每个 30 秒内讲完。
- 演示录屏 1 份 + 离线备份；现场网络或环境失败时的替代方案。
- 评委必问题库：为什么用 / 不用 LLM；如何在 3600 秒内完成；换隐藏种子是否仍成立；死亡掉落后如何恢复；token 如何控制；如何确认动作真的生效。

## 5. 时间倒排（建议，队内可调）

| 日期 | 交付 |
|---|---|
| 10-24 | 技术路线一句话、代码仓库地址、第一版架构图 |
| 10-31 | 第一次完整跑通记录（木 / 石 / 铁任一阶段） |
| 11-07 | 至少 3 组对照实验数据 |
| 11-14 | 报告所需素材冻结（图表、数据、引用） |
| 11-17 | 技术报告 PDF 初稿，队内审阅 |
| 11-19 | 代码 ZIP + 报告 PDF + 网页说明定稿 |
| 11-20 | 官方提交截止（具体时刻待确认） |
| 11-30 | 现场答辩（暂定） |

## 6. 数据与合规约定

- 只认真实运行产物；失败、超时、低分都记录，不补写、不估算。
- 不在仓库里写 API Key、token、cookie、账号密码或平台内部 ID。
- 录屏、模型权重等大文件不入库，放网盘或 Release，并在文档里留链接。
- 每次代码提交附一句变更说明，方便在报告里还原“改进过程”。
- 引用论文、开源代码、模型时写明来源、版本与实际改动。
- 正式测评只允许通过官方 LLM 端口联网；报告里不要出现任何绕过环境接口的做法。

## 7. 待确认

- 队内 A / B 两个角色分别由谁承担：只在内部渠道确认，不写入本仓库（公开仓库不留真实姓名）。
- 官网 Docker 镜像是否已可拉取，本地与正式环境是否一致。
- 平台“运行 3 次”是否各自独立享有 3600 秒 / 5M tokens。
- 技术报告是否必须严格沿用模板章节标题，还是允许合并小节。
